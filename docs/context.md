# The wiki: memory and progressive context

[README](../README.md) · [Docs](index.md)

## The wiki is the project's memory

An agent starts every session knowing nothing about the project. What it
said in a chat is gone when the session ends; what it keeps in a private
memory isn't seen by the next session, by a sub-agent, or by a teammate. So
the project's memory is its **wiki** — the docs in its repository — and
every decision is written there, by the role that took it, in the same
commit as the work it explains:

| What was decided | Where it is remembered | Written by |
|---|---|---|
| Why the product exists, what it is for | mission and vision | product owner, with the user |
| What to build, and in which order | epics, narratives, stories, milestones | product owner |
| How the system behaves today | the feature files, kept true by the tests | product owner, developer |
| How a story is built, and why | its plans: design, decisions, deviations, review | tech-lead, developer, reviewer |
| How the architecture is, and why it changed | decision records, constitution, standards | architect |
| What went wrong, and what was learned | issues, and every cycle's retro | maintainer, every role |

Rules that follow from it:

- **A decision left in the chat isn't taken.** The role skills offer to
  record every conclusion and write it once the user confirms. *Why:* the
  next session — and the next role — can only build on what it can read.
- **The wiki is the only place a rule lives.** Entry points, skills and
  prompts link to it; they never copy it. *Why:* a copy is a second version,
  and the two drift apart.
- **Records are added to, not rewritten.** An implemented story, a closed
  plan and a decision in force are history; a change is a new story, a
  superseding record or a dated revision. *Why:* memory that is rewritten
  loses why it changed.
- **The wiki is versioned and checked like code.** It lives in the
  repository, is reviewed with the change it explains, and the validator
  keeps it navigable: links resolve, `file:line` citations are current,
  every page is reachable from an index. *Why:* memory that silently rots is
  worse than none — it is believed.

## Progressive disclosure

A memory is only useful if the right part of it is found. An agent works
well with the right ten documents and badly with all two
hundred. Progressive disclosure is how a project lets an agent — or a
person — load only what its task needs: entry points stay thin, indexes say
what each document holds and when to read it, and every page links back up.

sanchin imposes the **format**, not the folder layout: where each directory
lives is the project's choice, mapped in the adapter.

## Thin entry points

`CLAUDE.md`, skills and agent prompts point to indexes; they never copy
rules. *Why:* a rule copied into an entry point is a second version of it,
and the two drift apart.

sanchin applies the rule to itself. Its process is not one long document
but a directory — an index, then one document per cycle — and its formats
likewise, one per artifact ([process/](process/index.md),
[artifacts/](artifacts/index.md)). Each role skill names the few documents
it reads — the index, the states, its own cycle, the working rules, the
formats it writes — instead of containing them or loading all of them.
*Why:* a role that loads the whole process spends its context on other
roles' work, and is invited to do it.

## Navigation index

For a directory whose documents are of different kinds. A table with three
columns:

| Document | What it contains | When to read it |
|---|---|---|
| [gates.md](gates.md) | The four gate levels and their rules. | When adding a check, or when one fails and it isn't clear what it guards. |

- **What it contains** describes the content, not its purpose.
- **When to read it** names the task or the symptom — "when adding a
  tool", "when gate X fails" — never "for more information". If a document
  is *not* needed where it might seem to be, say so.

## Catalog index

For a directory of items of one kind (decisions, issues, plans, stories):

- one **When to consult** line under the navigation line, for the whole
  catalog — a different "when" per decision record doesn't help anyone
  choose;
- one line per item describing its content: its title if that says enough,
  or a short summary.

Catalogs generated by a script keep the script's format; the "when" line is
written by hand outside the generated block.

## Navigation line

```text
CLAUDE.md                     points to docs/index.md — never copies a rule
└─ docs/index.md              what each area holds, and when to read it
   └─ architecture/index.md   one line per standard: what it says, when it applies
      └─ smells/god-module.md ← the one page the task needs
         [Docs](../../index.md) · [Architecture](../index.md)   ← the way back up
```

Every document except the docs root index starts with a line linking up:
`[Docs](../index.md) · [Architecture](index.md)`. *Why:* whoever lands on a
page — from a search, a link, a stack trace — can always climb to the index
that explains where they are.

## What is checked

| Rule | Checked by |
|---|---|
| Navigation line present | validator |
| Every directory with several documents has an index linking all of them and its child indexes | validator |
| Links resolve, `file:line` citations are current | validator, and the edit hook on every save |
| The what/when of each entry is accurate and useful | review |
